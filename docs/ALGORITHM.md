> 这份文档解释 HAE-NSG 每一步在做什么、为什么这样选，以及**哪些做法试过但失败了**。
> 后者往往比前面那些有用——省得别人再踩一遍。

## 处理链为什么长这样

这套结构经历过三次推翻，每次都是被一个具体的现象逼出来的。

**第一次：噪声被放大得比语音还狠。** 最初的实现是「测语音段 RMS → 除以目标电平得到
增益 → 整段乘上去」。逻辑上没问题，实际上一段 4 秒的录音里，底噪从 0.004 涨到了 0.032
（**放大了 8 倍**）。原因很简单：增益是按语音电平算的，而同一个增益作用在整段上，
安静的间隙被按同一倍数抬起来了。听起来像「嘶——」一直响。这一次修正引入了
**噪声门与增益解耦**：增益负责语音，门负责静音段，两者不共享乘数。

**第二次：谱减法把信噪比打崩了。** 按教科书的谱减法做，SNR 从 15.5 dB 掉到 3.83 dB。
看起来是算法实现错了，实际是**测量本身错了**——谱减压制的是频谱幅度，而 SNR 是按时域
RMS 算的，压制之后时域包络变得起伏，RMS 反而更接近语音峰值。这是一次「指标骗了自己」
的教训，也是后来改用「分段统计」（前半语音、后半纯底噪分别测）的原因。

**第三次：预加重撞上了增益上限。** 为了补高频，在增益之前做预加重，结果远场场景下
预加重把峰值推高，撞到 `max_gain` 的钳位，实际增益没拿到；同时因为电平被抬高，
`target_rms` 的比较基准也偏了。修正办法是**预加重后按原始 RMS 缩回**，让预加重只改变
频谱形状、不改变电平。

三次失败分别对应这份文档里的三节：噪声门判决、分段统计口径、预加重的电平保持。
每一节的「为什么」都能追到一个真实现象。

## 处理链

```
输入 float32 单声道
   │
   ├─ 1. 预加重（可选，仅 far/aggressive）
   │      一阶高通 y[n] = x[n] − a·x[n−1]
   │      再按混合比例混回原信号
   │      最后缩放回原始 RMS  ← 关键，见「教训 2」
   │
   ├─ 2. 帧能量聚类，得到静音掩码
   │      20 ms 一帧，算每帧 RMS
   │      两簇一维 k-means → 阈值 thr
   │      能量 < thr 的帧判为静音
   │
   ├─ 3. 增益（只按语音帧算）
   │      cur = RMS(非静音样本)
   │      gain = min(target_rms / cur, max_gain)
   │      整段 × gain
   │
   ├─ 4. 静音段压制（独立路径）
   │      静音样本 × (gate_attenuation / gain)
   │      净效果：静音段最终倍数 = gate_attenuation，与 gain 无关
   │
   └─ 5. 软限幅
          峰值 > knee 时 y = tanh(y/knee) · knee
```

中间计算全部 float64，只在返回时转 float32。

## 每一步的动机

### 1. 预加重：补偿远场的高频衰减

声音在空气里传播时高频衰减得比低频快。四五米外录到的语音，低频还在、高频已经糊了，
而辅音（s / sh / f / t）几乎全在高频——辅音丢了，ASR 会把 Spanish 听成 fan。

一阶高通把高频相对抬起来：

```
y[n] = x[n] − a·x[n−1]        a = 0.55（far）/ 0.65（aggressive）
```

然后按 `pre_emph_mix` 混回原始信号：

```
mixed = (1 − mix)·x + mix·y
```

`mix` 控制在 0.38 的原因：全量预加重会让声音发尖、齿音刺耳，混三成多刚好能听出区别
但不难听。

### 2. 静音检测：为什么不用固定分位数

判静音最直觉的做法是「取第 10 分位当门限」。这个做法有个隐蔽的坑：

**第 10 分位落在静音帧自身的分布内部**。如果一段录音里静音占 40%，那么第 10 分位大约
位于静音帧能量分布的下缘——用这个值当门限，只会判掉**最安静的 10%**，剩下 30% 的静音帧
全部漏判。漏判的帧随后被增益放大几十倍，底噪比处理前更响。

这里改成两簇一维 k-means：

```python
lo = percentile(energy, 10)
hi = percentile(energy, 90)
if hi <= lo * 1.5:          # 分不开，整段能量均匀，没有可判的静音
    return None
thr = (lo + hi) / 2
重复 12 次：
    quiet = energy < thr
    c_lo = mean(energy[quiet]);  c_hi = mean(energy[~quiet])
    thr = (c_lo + c_hi) / 2
if c_hi < c_lo * 2.0:       # 两簇中心太近，聚类没意义
    return None
```

`thr` 落在**两簇之间**而不是某一簇内部，这才是「分开语音和静音」想要的结果。
两个 `return None` 是安全阀：判断不出来时不做任何处理，而不是瞎判。

### 3 和 4. 增益与静音压制要一起算

这是整个库最核心的一点。

**错误做法**（先降噪再放大）：

```
1. 静音段 × 0.3
2. 整段 × 20
结果：静音段净倍数 = 0.3 × 20 = 6
```

底噪不但没降，反而响了 6 倍。测量上「降噪了 10 dB」，听起来更吵。

**正确做法**（静音段走独立路径）：

```
语音帧：× gain                    （gain 可以到 40 甚至 120）
静音帧：× (gate_attenuation / gain)
        净倍数 = gain × gate_attenuation / gain = gate_attenuation = 0.30
```

静音段的最终倍数**固定**为 `gate_attenuation`，与 `gain` 无关。所以：

- 把语音抬高 40 倍，底噪净降 10.5 dB（0.30 → −10.45 dB）
- 把语音抬高 120 倍，底噪还是净降 10.5 dB

这条性质在 `process` 里就是一行：

```python
out = y * gain
out[quiet] *= gate_attenuation / max(gain, 1.0)
```

### 5. 软限幅：为什么用 tanh

增益把峰值推过 1.0 就会硬削波。硬削波产生方波，方波的谐波在频谱上是一串等间距的
竖线——ASR 的声学模型没见过这种东西，会把整句话听错。

`tanh` 是平滑压缩，不会产生高频谐波：

```
y = tanh(x / knee) · knee
```

`knee = 0.85` 表示 0.85 以下完全线性，往上逐渐变软，输出渐近于 0.85 但永远不到 1.0。

`near` 和 `denoise` 用 0.97（几乎不动），`far` 和 `aggressive` 用 0.85（确实需要压）。

## 教训：试过但失败的四个做法

### 教训 1：谱减法把 SNR 从 15.5 dB 打到 3.83 dB

最早版本用经典谱减法（估计噪声谱 → 从幅度谱里减掉 → 重建）。

实测结果：输入 SNR 15.5 dB，输出 3.83 dB。**看起来是灾难性的倒退**。

拆开看是两件事叠在一起：

1. **测量假象**：谱减普遍会削掉语音段里的气声和辅音，而「语音功率」是按整段 RMS 算的，
   削掉之后 RMS 下降，分母（噪声功率）却按新的噪声底算——SNR 定义在这种非线性处理上
   已经不成立。
2. **真实损伤**：音乐噪声（musical noise）确实存在。残留的随机谱峰听起来像水泡声，
   比原来的平稳底噪更难忍。

结论：谱减不适合放在 ASR 前端。它对「人耳听起来干不干净」有用，对「模型能不能认出字」
经常是负作用，因为模型需要的是辅音完整，不是背景安静。

### 教训 2：预加重会把电平抬起来，然后撞上 max_gain

一阶高通 `y[n] = x[n] − a·x[n−1]` 理论上会让 RMS 变大（高频被强调）。
`far` 预设里 `max_gain = 40`，如果预加重先把 RMS 抬了 1.5 倍，那么 40 倍的预算里
有 1.5 倍被预加重吃掉了，剩下的增益就不够。

修法是在预加重之后**按原始 RMS 缩放回去**：

```python
r0 = sqrt(mean(x²))
r1 = sqrt(mean(y²))
if r1 > eps and r0 > eps:
    y *= r0 / r1        # 只改频谱形状，不改电平
```

这样预加重只影响频谱，增益预算完全留给真正的音量提升。

### 教训 3：静音段只用 1/gain 封顶，等于没降噪

中间版本用的是：

```python
out[quiet] *= min(gate_attenuation, 1.0 / gain)
```

当时的设计理由是「保证底噪不超过原始电平」。但推一下：

- `gain = 20` 时，`1/gain = 0.05`，`min(0.30, 0.05) = 0.05`
- 静音段净倍数 = `20 × 0.05 = 1.0`

**净倍数恰好等于 1** —— 底噪回到原始电平，不多不少。这只是「没更吵」，谈不上降噪。

改成固定倍数之后（`gate_attenuation / gain`），净倍数恒为 0.30，底噪净降 10.5 dB，
而且这个 10.5 dB 与增益是多少无关。

### 教训 4：噪声门不能做峰值保护

`noise_gate` 单独调用时，直觉上应该加一句「如果输出峰值超了就整体缩一下」。这是错的。

门控只会把样本**乘小**，绝不会让峰值变大。如果在这里做统一缩放，被缩的是**整段**——
包括那一半本来一个样本都没动的语音帧。「语音零损伤」的承诺当场破掉。

所以 `noise_gate` 里明确写了不做峰值保护，并在注释里留下理由。

## 为什么不做得更复杂

这个库的定位很窄：**ASR 之前的增益与静音段压制**。所以刻意不做下面这些事：

| 不做 | 原因 |
|---|---|
| 频域降噪 / 谱减 | 见教训 1，对 ASR 常常是负作用 |
| 神经网络降噪 | 需要模型文件、CPU 开销大一个量级，且和「零依赖」冲突 |
| VAD | 语义级判断是另一个问题，单独在 [HAE-VAD-Core](https://github.com/eyru/HAE-VAD-Core) |
| 立体声 / 多声道 | 只会让接口和测试复杂一倍，实际用途几乎没有 |
| 自动选预设 | 选错了比不选更糟，交给人决定 |

简单的东西能做到「对清楚录音零损伤」，这个承诺比「降噪能力强」更重要——
ASR 前端最怕的不是没能变好，而是把本来能认的句子搞坏。

## Python 与 C++ 的等价性

两套实现逐样本一致（误差 < 1e-6），靠的是三条约定：

1. **中间计算一律 float64**，只在最后转 float32。float32 中间态在长信号上会累积误差。
2. **不用任何「库之间可能有差异」的函数**。分位数自己算（`pos = (n−1)·p/100`，
   线性插值写死），排序用稳定排序，k-means 迭代次数写死 12 次、收敛阈值 1e-9。
3. **不用 SIMD 友好的重排**。numpy 的 `mean` 和 C++ 的累加顺序不同，浮点加法不满足
   结合律，所以两边都用 float64 累加，误差落在 1e-9 量级，远小于 float32 的 1e-7。

`tests/run_parity.py` 会编译 C++ 版并对 8 种信号 × 4 个预设共 32 组逐样本比对，
最大绝对误差必须 < 1e-6。
